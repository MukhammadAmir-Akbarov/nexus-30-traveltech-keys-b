# TurizmHamroh · Кейс B «Надёжный и персонализированный спутник туриста»

Прототип для хакатона NEXUS30, трек TravelTech, партнёр — Комитет по туризму.
Три функции кейса живут в одном контексте поездки, а не как три отдельных продукта.

## Запуск

```bash
npm install
npm run dev      # http://localhost:3000
npm run check    # самопроверка: поиск по корпусу, планировщик, подбор гида
npm run build    # прод-сборка
```

Без ключей приложение полностью работоспособно: включается offline-режим
(правила + предзаписанные ответы). Чтобы подключить модель:

```bash
cp .env.example .env.local
# AI_GATEWAY_API_KEY=...
```

## Соответствие требованиям кейса

| № | Требование кейса | Реализация |
|---|---|---|
| 1 | Достоверная туристическая информация | `/check` — ответ строится только по корпусу источников, всегда со ссылкой; нет данных → «нет данных» |
| 2 | AI trip-planner | `/plan` — structured output модели, санитайзинг id, карта с порядком осмотра |
| 3 | Сценарий одиночного путешественника | отдельная памятка на `/plan` и `/guides`, подтверждённый статус гида весит больше именно в соло-формате |
| 4 | Поиск подходящего гида | `/guides` — регион, несколько языков, пол, транспорт, отзывы, критерии подтверждения + объяснение «почему он» |
| 5 | Единый пользовательский опыт | `TripProvider` — общий контекст на все вкладки, виден в шапке на каждом экране |
| §4.2 | Персонализированный трансфер | на каждом переезде поезд / машина / микроавтобус со временем и ориентировочной ценой; поезд только на реальных направлениях |
| §9 | Механизм подтверждения гида | в карточке видно, что проверено: лицензия, реестр, личность, языки, дата; у непроверенного — предупреждение |
| §3 | Спутник «во время поездки» | PWA: ставится на телефон и открывается без сети, последний маршрут и проверки кэшируются |

### Сверх ТЗ

- **Репутация гида по фактчеку.** При проверке можно указать, чьи слова проверяются.
  Вердикты копятся по гиду и влияют на подбор: «фактов подтвердилось 0% (3 проверок)»
  опускает его в выдаче. Это замыкает три модуля кейса в один цикл:
  проверка → репутация → подбор.
- **QR у объектов**: `/qr` — лист кодов на печать, `/place/[id]` — карточка с фактами,
  источниками и озвучкой; сканер на штатном `BarcodeDetector`.
- **Обмен поездкой**: контекст кодируется в ссылку и QR, получатель видит тот же маршрут.
- **Летний режим**: объекты под открытым небом уходят в начало дня с пометкой
  «летом днём выше +38» (основано на факте c34 из корпуса).
- **Рейтинг гида по объектам, а не общий.** Гид может отлично вести Центр исламской
  цивилизации и не знать Регистана — общая оценка это скрывает. Точность считается
  отдельно по каждому объекту и подставляется под объекты предстоящего маршрута.
- **Инфраструктура по маршруту**: заправки (отдельно метан и бензин), туалеты,
  намазхона, медпункт и кафе — ближайшие к точке дня одним раскрытием.
- **Пять способов переезда**: самолёт, поезд, автобус, машина, микроавтобус —
  со временем и ориентировочной ценой; рейсы и поезда только на реальных направлениях.
- **Даты поездки календарём** и **несколько регионов сразу**.
- **Что смотреть внутри объекта**: у комплекса Имама Бухари — мавзолей, музей рукописей,
  мечеть; турист понимает, что его ждёт, ещё до поездки.
- **Вход и админка**: `/login` для туристов, `/admin` для администратора — управление
  гидами, фактами источников, пользователями и экспорт правок в JSON.

## Архитектура

```
src/
├── app/
│   ├── page.tsx            выбор контекста поездки (регион, интересы, формат, дни)
│   ├── check/              проверка фактов (текст + голос)
│   ├── plan/               маршрут по дням + карта
│   ├── guides/             подбор гида
│   └── api/{check,plan,guides}/route.ts
│   ├── place/[id]/         карточка объекта по QR: факты, источники, озвучка
│   ├── qr/                 лист QR-кодов на печать
│   ├── login/ + admin/     вход и панель администратора
│   └── api/{check,plan,guides,admin,auth}/
├── components/
│   ├── TripProvider.tsx    единый контекст + язык + тема + localStorage
│   ├── Nav.tsx             вкладки, переключатели языка и темы, полоса контекста
│   ├── RouteMap.tsx        Leaflet: точки, нумерация, линия маршрута
│   ├── TransferCard.tsx    выбор способа переезда между городами
│   ├── VoiceInput.tsx      непрерывная запись речи гида (Web Speech API)
│   ├── QrScanner.tsx       сканер на штатном BarcodeDetector
│   ├── SpeakButton.tsx     озвучка карточки (SpeechSynthesis)
│   ├── SoloPanel.tsx       памятка одиночному путешественнику
│   ├── ShareTrip.tsx       поездка ссылкой и QR
│   ├── Onboarding.tsx      короткий опрос при первом входе
│   ├── OfflineReady.tsx    сервис-воркер и плашка «нет сети»
│   └── Footer.tsx
├── data/                   демо-датасет: 18 объектов, 10 гидов, 40 абзацев корпуса, кэш демо
└── lib/                    i18n, retrieval, planner, transfer, match, auth, store, selftest
```

Одна команда закрывает всю нетривиальную логику: `npm run check` — поиск на трёх языках,
планировщик (группировка дней, мультигород, переезды, летнее правило), подбор гида
(фильтры, репутация, соло-режим), полнота переводов и авторизация (подпись, подделка
роли, просрочка).

### Языки и тема

- **Интерфейс на трёх языках** — узбекский (по умолчанию), русский, английский.
  Словарь один: `src/lib/i18n.ts`. Мультиязычны и данные: названия объектов, описания
  гидов, заголовки источников, а также генерируемые тексты — заметки маршрута и
  объяснение «почему этот гид».
- **Корпус источников остаётся на языке оригинала** (русский) и не переводится: это канон.
  Кроссязычный поиск решён словарём алиасов (`Registon → Регистан`, `Kalyan → Калян`, …)
  в `retrieval.ts` — ~30 записей вместо мультиязычных эмбеддингов. Модель получает
  русские отрывки, а отвечает на языке интерфейса.
- **Тема**: светлая / чёрная / системная, выбор хранится в `localStorage`, применяется
  инлайн-скриптом до первой отрисовки — белого мига при загрузке нет. Тайлы карты в
  тёмной теме инвертируются, чтобы не слепить на демо.

### Технические решения и почему так

- **Поиск по источникам без БД и эмбеддингов.** 40 абзацев — это IDF по префиксам слов
  в `src/lib/retrieval.ts`. Postgres + pgvector имеет смысл от ~500 абзацев;
  интерфейс `retrieve()` при переходе не меняется.
- **Модель через Vercel AI Gateway** строкой `"provider/model"` — без SDK конкретного
  провайдера, модель меняется одной переменной окружения.
- **Модель не выдумывает объекты.** `sanitize()` в `/api/plan` выбрасывает id, которых нет
  в датасете, и дубли. Пустой результат → правило-основанный маршрут.
- **Модель не выдумывает факты.** В `/api/check` ей передаются только найденные отрывки;
  инструкция — при отсутствии ответа ставить `unclear`.
- **Карта на CircleMarker, а не Marker** — не нужны PNG-иконки Leaflet, которые ломаются
  при сборке бандлером.
- **Голос — штатный Web Speech API.** В браузерах без поддержки кнопка просто скрывается.

### Устойчивость демо

Любой сбой сети или LLM не ломает показ:

| Ситуация | Поведение |
|---|---|
| Нет `AI_GATEWAY_API_KEY` | всё работает на правилах и предзаписанных ответах |
| LLM отвечает >20 с или падает | `abortSignal` → откат на офлайн-ответ |
| Репетиция без интернета | `DEMO_OFFLINE=1` принудительно включает офлайн |

Режим ответа честно показан в интерфейсе меткой «ответ модели» / «офлайн-режим».

## Данные и приватность

- Все данные об объектах, гидах и источниках — **демонстрационные**, персональных данных нет.
- Приложение не собирает данные пользователя: контекст поездки хранится в `localStorage`
  браузера и на сервер уходит только как параметры запроса.
- Метка «проверенный гид» — демо-признак. В рабочей версии подтверждается официальным
  реестром Комитета по туризму (источник уточняется у партнёра).

## Что осознанно не делали

Авторизацию, бронирование и оплату гидов, админку, нативное мобильное приложение,
реальные интеграции с внешними API. Ничего из этого не влияет на критерии оценки
и не входит в ожидаемый формат результата.
