# TurizmHamroh · Кейс B «Надёжный и персонализированный спутник туриста»

Прототип для хакатона NEXUS30, трек TravelTech, партнёр — Комитет по туризму.
Три функции кейса живут в одном контексте поездки, а не как три отдельных продукта.

## Запуск

```bash
npm install
npm run dev      # http://localhost:3000
npm run check    # самопроверка: поиск по корпусу, планировщик, подбор гида
npm run build    # прод-сборка
```

Без ключей приложение полностью работоспособно: включается offline-режим
(правила + предзаписанные ответы). Чтобы подключить модель:

```bash
cp .env.example .env.local
# AI_GATEWAY_API_KEY=...
```

## Соответствие требованиям кейса

| № | Требование кейса | Реализация |
|---|---|---|
| 1 | Достоверная туристическая информация | `/check` — ответ строится только по корпусу источников, всегда со ссылкой; нет данных → «нет данных» |
| 2 | AI trip-planner | `/plan` — structured output модели, санитайзинг id, карта с порядком осмотра |
| 3 | Сценарий одиночного путешественника | `travelType` (`solo/family/group`) влияет на отбор объектов и на подбор гида |
| 4 | Поиск подходящего гида | `/guides` — подбор по региону, языку, интересам и формату + объяснение «почему он» |
| 5 | Единый пользовательский опыт | `TripProvider` — общий контекст на все вкладки, виден в шапке на каждом экране |

## Архитектура

```
src/
├── app/
│   ├── page.tsx            выбор контекста поездки (регион, интересы, формат, дни)
│   ├── check/              проверка фактов (текст + голос)
│   ├── plan/               маршрут по дням + карта
│   ├── guides/             подбор гида
│   └── api/{check,plan,guides}/route.ts
├── components/
│   ├── TripProvider.tsx    единый контекст + localStorage
│   ├── Nav.tsx             вкладки и полоса контекста
│   ├── RouteMap.tsx        Leaflet: точки, нумерация, линия маршрута
│   └── VoiceInput.tsx      Web Speech API браузера
├── data/                   демо-датасет: 18 объектов, 10 гидов, 40 абзацев корпуса, кэш демо
└── lib/                    retrieval, planner, match, model, selftest
```

### Технические решения и почему так

- **Поиск по источникам без БД и эмбеддингов.** 40 абзацев — это IDF по префиксам слов
  в `src/lib/retrieval.ts`, 60 строк. Postgres + pgvector имеет смысл от ~500 абзацев;
  интерфейс `retrieve()` при переходе не меняется.
- **Модель через Vercel AI Gateway** строкой `"provider/model"` — без SDK конкретного
  провайдера, модель меняется одной переменной окружения.
- **Модель не выдумывает объекты.** `sanitize()` в `/api/plan` выбрасывает id, которых нет
  в датасете, и дубли. Пустой результат → правило-основанный маршрут.
- **Модель не выдумывает факты.** В `/api/check` ей передаются только найденные отрывки;
  инструкция — при отсутствии ответа ставить `unclear`.
- **Карта на CircleMarker, а не Marker** — не нужны PNG-иконки Leaflet, которые ломаются
  при сборке бандлером.
- **Голос — штатный Web Speech API.** В браузерах без поддержки кнопка просто скрывается.

### Устойчивость демо

Любой сбой сети или LLM не ломает показ:

| Ситуация | Поведение |
|---|---|
| Нет `AI_GATEWAY_API_KEY` | всё работает на правилах и предзаписанных ответах |
| LLM отвечает >20 с или падает | `abortSignal` → откат на офлайн-ответ |
| Репетиция без интернета | `DEMO_OFFLINE=1` принудительно включает офлайн |

Режим ответа честно показан в интерфейсе меткой «ответ модели» / «офлайн-режим».

## Данные и приватность

- Все данные об объектах, гидах и источниках — **демонстрационные**, персональных данных нет.
- Приложение не собирает данные пользователя: контекст поездки хранится в `localStorage`
  браузера и на сервер уходит только как параметры запроса.
- Метка «проверенный гид» — демо-признак. В рабочей версии подтверждается официальным
  реестром Комитета по туризму (источник уточняется у партнёра).

## Что осознанно не делали

Авторизацию, бронирование и оплату гидов, админку, нативное мобильное приложение,
реальные интеграции с внешними API. Ничего из этого не влияет на критерии оценки
и не входит в ожидаемый формат результата.
